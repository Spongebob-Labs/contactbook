## 0. Orientation for the executor

**Assume you have zero context for this repo. Read this whole section before writing code.**

### 0.1 What this project is
Contact Book 2.0 — a digital contact-card product. A user builds a **card**, which is a
*filter over their own profile fields*. The card's payload is a **QR code**: a scanner
points a phone at it, lands on `/c/{slug}`, and taps "Save to contacts" to download a
`.vcf`. The QR is a functional optical target and is the single thing in this build that
can be **objectively wrong**.

The monorepo is pnpm + Turbo-less workspaces: `apps/web` (Next.js 16), `apps/api`
(NestJS), `packages/types`, `packages/utils`. **This run touches `apps/web` only.**

`apps/web` today is a bare `create-next-app` scaffold: `src/app/{layout,page,globals.css}`,
`src/lib/api.ts`, five scaffold SVGs in `public/`. There is no design system, no component,
no test. Everything in this plan is new.

### 0.5 The mandatory screen pattern (copy this — every data screen uses it)
`useFixture()` reads `?state=` via `useSearchParams()`, so it is client-side and **must**
sit under `<Suspense>`. Every data route is therefore a two-file pair:

```tsx
// src/app/(app)/cards/page.tsx        (server component)
import { Suspense } from 'react';
import { CardsListClient } from './cards-list-client';
import { CardsListSkeleton } from './cards-list-client';

export default function CardsPage() {
  return (
    <Suspense fallback={<CardsListSkeleton />}>
      <CardsListClient />
    </Suspense>
  );
}
```
```tsx
// src/app/(app)/cards/cards-list-client.tsx
'use client';
import { useFixture } from '@/lib/fixture-gateway';

export function CardsListClient() {
  const { state, data, error } = useFixture((db) => db.cards);
  // switch over state -> loading | empty | empty-filtered | error | offline | success
  // the returned root element MUST carry data-screen-state={state}
}
```
Non-negotiable: the client component's **root element carries `data-screen-state`**
(spec §13.2) — every state and a11y sweep keys off it.

### 2.1 Why wave 1 is a single agent
`apps/web/package.json` is one file and every subsequent track needs its dependencies and
its test runners installed. Faking parallelism here would mean two agents editing
`package.json`, which is exactly the failure this plan exists to prevent. T01 is the
bottleneck and it is short (~20 minutes).

### 2.2 Two deliberate scheduling decisions
- **T26 (marketing) lists `T25` in `depends_on` although it has no code dependency on it.**
  That edge is a *scheduling* edge. Spec §3.5 names the marketing site the **cut-first**
  surface, so it must be the last product surface built: if the run slips, marketing is what
  slips. Real code dependencies of T26 are T13 and T14 only.
- **T32 owns no files.** It is a read-only verification track: it runs the three gates and
  the full suite, pastes real output, and reports. It cannot fix anything — failures it
  finds go into Stage C's §5.3 fix rounds, which cluster by owning file.

## 8. Out of Scope Reminder — restated verbatim from the spec

> **§3.1 — Vansh, Q5:** *"Our work is to just make the Ui nothing else API integration will
> be doing at last."*
>
> **No executor may write a network call, a data-fetching hook, an auth guard, a server
> action that talks to a backend, a database query, an environment-variable-driven API
> client, or a mock server.**

> scope decision that makes a build of this size finishable.
